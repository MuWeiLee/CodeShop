# 架构说明

## 分层

```
客户端小程序   导购端小程序   商家端后台   平台运营端后台        ← 四个端，只调接口
        │            │            │              │
        └────────────┴─────┬──────┴──────────────┘
                           ▼
                 apps/server（NestJS）                      ← 接口、事务、持久化
     扫码 · 服务记录与归属 · 导购券 · 订单 · 码 · 规则配置
                           │
                           ▼
                packages/domain（纯 TypeScript）            ← 业务规则，无 I/O
      nextBinding · attributeOrder · 导购券资格与计算 · 码格式与签名
                           │
                           ▼
              PostgreSQL（开发和测试用 PGlite）
```

规则集中在 `packages/domain`：纯函数，不读写数据库，不依赖框架，所以 PRD 第 4 节的每条规则都能直接单测。服务端只负责「读出现状 → 调规则 → 把结果写回」，并保证事务和并发正确。前端也可以复用其中的展示函数（`formatYuan`、`describeDiscount`、`parseQrToken`）。

依赖 `node:crypto` 的导购动态码签名放在子路径 `@codeshop/domain/server`，避免被打进前端包。

## 数据模型

表结构见 `apps/server/src/db/schema.ts`，迁移 SQL 在 `apps/server/drizzle/`。

| 表 | 作用 | 关键约束 |
| --- | --- | --- |
| `merchants` / `merchant_settings` | 商家与规则配置 | 无配置时用 PRD 默认值 |
| `stores` / `guides` | 门店（含 GCJ-02 坐标）、导购（当班、陈列区、本人顾客账号） | 均带 `merchant_id` |
| `customers` | 顾客账号，平台层一人一个 | — |
| `spus` / `skus` / `store_samples` | 款、规格、门店样品（决定「店内可试」） | — |
| `codes` | 商品码、实体导购卡、订单码 | 同店同款只有一个有效商品码（部分唯一索引） |
| `service_records` | 每一次接触：扫码、分配、开单、跟进、转移 | 按「顾客 × 商家 × 时间」建索引 |
| `bindings` | 顾客在某商家的导购绑定 | 主键「顾客 × 商家」，保证每商家最多一个 |
| `coupons` | 已发放的导购券，发放时快照规则 | — |
| `order_drafts` / `orders` | 导购开单草稿、订单 | 订单记录归属结果与依据的服务记录 ID |

金额一律用整数「分」；时间一律带时区。

## 关键设计

**服务记录是归属的唯一依据。** 每次接触写一条服务记录，绑定变化由 `nextBinding(当前绑定, 新记录, 规则)` 算出；下单时 `attributeOrder` 根据绑定和最近到店记录判定归属，并把依据的服务记录 ID 写进订单。出现归属争议时，可以从订单一路追溯到具体哪次扫码。

**并发。** 同一顾客在同一商家的扫码、领券、下单，在一个事务内完成，并用 `pg_advisory_xact_lock` 按「顾客 × 商家」串行化。这样「7 天限领 1 张」和绑定覆盖在并发下依然成立（有对应测试）。导购开单草稿用行锁，防止同一张开单被下两次。

**多商家隔离。** 除顾客账号外，每张业务表都带 `merchant_id`，服务层查询一律按商家过滤；绑定、券、服务记录都按「顾客 × 商家」存储。领域函数在绑定与记录不属于同一「顾客 × 商家」时直接抛错，防止数据串用。

**价格与优惠以服务端为准。** 客户端只传规格和数量，价格从数据库读，优惠在同一事务内重新计算并按比例分摊到每一行（部分退货时据此扣回）。

**二维码只放 token。** 商品码和订单码是随机 ID，导购动态码是 HMAC 签名、60 秒刷新，二维码里不含价格和个人信息。二维码内容是 `QR_BASE_URL/q/<token>` 形式的链接，配合小程序后台的「扫普通链接二维码打开小程序」，用微信扫一扫就能直接打开。

**定位只在扫实体导购卡时用一次。** 校验半径由商家配置（默认 200 米），失败则不绑定、不发券；定位精度比半径还差时按失败处理。门店坐标与顾客上报坐标统一使用 GCJ-02，混用 WGS-84 会差出几百米。

## 安全

- **登录尚未接入。** 目前用 `AUTH_MODE=dev` 通过请求头模拟三种身份，仅限本地开发；默认 `AUTH_MODE=none`，所有需要登录的接口都返回 401。
- **生产环境配置不全时拒绝启动**：`AUTH_MODE=dev`、缺 `GUIDE_CODE_SECRET`、缺 `DATABASE_URL`、`QR_BASE_URL` 仍为占位值，任一情况都会报错退出。
- 导购动态码签名用常数时间比较；密钥至少 32 个字符。
- 请求体用 zod 校验，业务规则拒绝统一返回 `{ error: { code, message, details } }`。

## 尚未接入

| 能力 | 说明 |
| --- | --- |
| 正式登录 | 顾客：`wx.login` 换 openid；导购：账号或企业微信；商家与平台：账号密码。替换 `AuthGuard` 即可，接口不变 |
| 微信支付与分账 | 订单目前停在 `pending_payment`。分账需走持牌支付机构，避免资金二次清算（PRD 10.4） |
| 佣金结算 | 订单已记录归属和是否计佣；冻结期、扣回、结算单待开发 |
| 同设备识别 | 目前只比对同手机号，同设备需客户端上报设备指纹 |
| 物流、ERP、仓库 | 需要商家提供接口 |
| 数据库约束 | 枚举字段目前由应用层保证，可补充 CHECK 约束 |

| 部分 | 选型 | 版本线 |

| 语言 | TypeScript | 5.9 |
